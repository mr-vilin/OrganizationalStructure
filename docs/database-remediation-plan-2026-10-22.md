## 2. 管理员会话改为摘要存储

### 现状

当前 `admin_session.id` 同时作为数据库主键和 `org_session` Cookie 值。数据库保存的是可直接用于认证的会话值，违反“不存储可直接使用凭据”的要求。

### 推荐设计

增加 `token_digest` 字段，`id` 恢复为内部会话记录标识：

- Cookie 保存随机生成的会话令牌；
- 数据库只保存令牌的 SHA-256 摘要；
- `token_digest` 使用 `CHAR/VARCHAR(64)`、`utf8mb4_bin`、唯一索引；
- 认证时先计算 Cookie 摘要，再按摘要查询；
- `id` 只用于数据库记录、注销和审计关联；
- Cookie、日志、异常和审计数据不得写出令牌原文。

### 旧数据迁移

旧会话值不能继续留在数据库中。迁移安排如下：

1. 停止应用、worker 和事件监听的写入。
2. 备份数据库并保存会话行数、过期数和撤销数。旧主键本身是令牌，只能留在受限加密备份中，不进入普通快照或日志。
3. 增加 `token_digest` 临时可空字段。
4. 将现有会话全部标记为撤销，并把旧值转换为摘要；同时把 `id` 替换为新的随机内部标识，避免旧原文继续留在数据库。
5. 校验摘要唯一性和会话行数，确认没有外键或应用外部引用后，再收紧字段约束。
6. 启动新版本，所有管理员重新登录。

迁移脚本和日志只记录数量、状态和校验结果，不打印旧令牌、新令牌或摘要清单。当前检查确认 `admin_session` 没有数据库外键引用，但执行前仍需重新检查目标环境。

### 验收

- 新登录成功，Cookie 值与数据库摘要不同；
- 直接把数据库摘要当作 Cookie 不能认证；
- 旧 Cookie 全部失效；
- 注销、过期、删除白名单、停用员工和 CSRF 校验继续有效；
- 数据库中不存在旧会话原文；
- 真实 HTTPS 入口完成登录、刷新和注销验证。

这项迁移不是普通可逆字段变更。失败时使用修复后的兼容版本继续完成摘要迁移，不把摘要还原成令牌，也不恢复旧会话有效性。

涉及文件：`backend/app/feishu/oauth.py`、`backend/app/persistence/repositories.py`、`backend/app/main.py`、`backend/app/dependencies.py`、会话模型、迁移和认证测试。

## 3. 修复 0006 迁移的安全性

当前 `0006_column_comments.py` 的 `downgrade()` 会重新构造 `MODIFY COLUMN`，但没有保留默认值、字符集、排序规则、自增属性和完整注释。它可能改变字段定义，也可能在部分 DDL 已提交后失败。

### 处理原则

- 不在真实业务库上先降级到 0005 来修复 0006；
- 离线模式不依赖 `sa.inspect()` 或实时数据库反射；
- 每个历史迁移使用固定字段快照，不引用会变化的当前 ORM；
- 升级和回退均保留字段类型、空值、默认值、字符集、排序规则、自增、生成表达式、索引和约束；
- 回退只恢复 0005 已有的注释，不清空 0004/0005 新增字段的原始说明；
- 在线执行前比较实际元数据，发现未预期差异时停止，不覆盖人工修改。

### 根据部署范围选择

**如果 0006 只存在本机或尚未对外发布：**

- 修复 0006 的确定性升级和回退；
- 在独立 MySQL 中验证 `0005 → 0006 → 0005`；
- 确认字段定义和数据逐项一致后再继续后续迁移。

**如果 0006 已部署到其他环境：**

- 不重写已发布迁移的业务语义；
- 将危险回退改为在执行任何 DDL 前明确阻断；
- 通过新的正向迁移提供后续结构修复；
- 把 0006 的回退限制和恢复方式写入部署说明。

无论选择哪条路径，都要验证：新建数据库、从旧版本升级、已到 0006 的数据库继续升级、离线 SQL 生成、迁移中断后的重试和最终结构对比。

## 4. 统一字符集、排序规则和连接会话

### 推荐目标矩阵

| 对象 | 目标设置 |
| --- | --- |
| 数据库默认值 | `utf8mb4 / utf8mb4_general_ci` |
| 业务表默认值 | `utf8mb4 / utf8mb4_general_ci` |
| 普通文本列 | `utf8mb4_general_ci`，执行前逐列确认 |
| 来源 ID、业务键、关联字段 | 保持 `utf8mb4_bin` |
| 应用、迁移、worker、事件监听连接 | 显式设置 utf8mb4、`utf8mb4_general_ci`、`time_zone='+00:00'` |
| 事务隔离级别 | 保持 `REPEATABLE READ` |
| 恢复建库入口 | 与目标数据库默认值一致 |

修改前必须完成：

- 所有唯一键冲突检查；
- 大小写、重音、尾空格比较检查；
- 外键兼容性和孤儿数据检查；
- 业务查询和排序行为检查；
- 生产环境真实数据量和锁影响评估。

不能把整张表一律转换为普通文本排序规则，因为显式 `utf8mb4_bin` 的稳定 ID 字段必须保留。ORM、Alembic、Compose、连接工厂和恢复文档必须显式声明规则，不能依赖服务器默认值。

本次已选择 `utf8mb4_general_ci`，因此执行列转换并在项目规范中记录：普通文本使用 `general_ci`，稳定 ID 使用 `bin`；数据库、业务表、连接和恢复入口均显式声明同一普通文本规则。

## 5. 对齐 ORM、迁移和实库元数据

- 补齐 137 个业务字段的 ORM 中文注释；
- 统一当前实库已有的 13 处注释文本差异；
- 给 21 张业务表增加准确的中文表注释；
- 在 ORM 中表达实际存在的 5 个 `server_default`，包括 JSON 空对象和 4 个任务计数的 0；
- 更新会话字段注释，明确其最终是内部标识还是令牌摘要；
- 0001—0005 作为历史基线保留，新增迁移直接满足字段注释和表注释要求；
- 增加只读结构检查，覆盖版本、表、字段、注释、默认值、排序规则、主键、外键、唯一键和普通索引。

Alembic 的常规比较不足以覆盖所有排序规则和 JSON 默认值差异，因此需要补充项目自己的结构检查，不把“ORM 比较无差异”当成完整结论。

## 6. 加强就绪检查

`/health/ready` 应只读检查：

- 数据库连接是否可用；
- `alembic_version` 是否只有一个版本且等于当前构建支持的 head；
- 必要表和关键字段是否存在；
- 关键单例是否可读取。

健康检查不得执行白名单初始化、迁移、数据写入或状态修复。版本为空、旧版本、未知 head、关键表缺失或数据库断开时返回明确的 503 错误码。

组织初始化 `pending` 不应阻断管理员进入管理端，否则无法完成初始化；但业务读取接口继续返回初始化未完成。数据库 ready、应用 healthy、组织初始化完成和飞书覆盖验收必须分别报告。

## 7. 初始化和飞书降级单独诊断

当前有一个 `initialize/queued` 任务、一个等待初始化的 `reconcile` 任务，`dataset_state.initialization_status` 为 `pending`，飞书连接为 `degraded`。

后续只读诊断应检查：

- worker 是否运行、租约是否有效；
- 初始化任务的阶段、错误码和重试次数；
- 飞书应用、租户绑定和权限配置；
- 事件监听与远程回查状态；
- 数据集世代和任务队列是否一致。

不得直接把 `initialization_status` 改成 `complete`，也不得因数据库结构修复自动触发全量同步或清理业务数据。

建议将后续变更拆为两个正向迁移：

- `0007_schema_alignment`：注释、默认值、表/列排序规则和结构一致性；
- `0008_session_digest`：会话令牌摘要、旧会话撤销和安全迁移。

两者分开可以避免把元数据调整和不可逆的会话凭据转换混在同一个“可整体回滚”的承诺中。

## 9. 验收与恢复边界

验收必须取得以下证据：

- 新旧会话行为、摘要查询、旧 Cookie 失效和 CSRF 测试；
- 独立 MySQL 往返迁移后的字段、索引、约束、默认值、自增和数据对比；
- 完整离线 SQL 生成和新库执行记录；
- ORM、迁移和实库结构检查报告；
- 应用各进程首次连接和重连后的会话参数；
- 数据、外键、唯一键和会话迁移数量核对；
- 健康检查不写库且能区分 schema ready 与 initialization pending；
- 独立环境中的备份恢复、迁移中断和恢复后凭据撤销验证。

真实数据库执行前必须重新确认开发、测试、生产环境的库名、版本、迁移版本、数据量和连接参数，保存受限备份和结构快照。MySQL DDL 可能提交，失败恢复不能假设一次事务会撤回全部 DDL；会话摘要也不能还原为旧令牌。
