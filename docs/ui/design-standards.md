# 项目设计规范

本规范适用于 OrganizationalStructure 所有面向用户的页面设计、开发与验收。以下规则于 2026-10-26 由用户确认；历史原型或现有页面与本规范不一致时，以本规范为准。

## 配置与录入使用结构化表单

- 除非需求明确要求用户直接编辑 JSON，否则不得让用户通过填写或粘贴 JSON 完成配置，也不得自行提供“高级模式”“源码模式”等 JSON 编辑入口。
- 选项列表、字段映射、键值对等多条目配置，一律采用手动加行的形式，支持新增、逐行编辑和删除。
- 每行按业务含义拆分为独立字段，使用明确的中文标签；根据字段类型使用输入框、选择器等控件，不要求用户理解大括号、引号、逗号等 JSON 语法。
- 系统负责将表单数据转换为接口需要的 JSON，并将已保存的数据还原为可编辑的表单行。接口或数据库使用 JSON，不构成界面使用 JSON 输入框的理由。
- 必填、重复标识及其他已确认的业务约束在对应行和字段旁提示；校验或保存失败时保留用户已填写的内容，不让用户依靠 JSON 解析错误排查输入。
- 只有对应需求明确提出直接编辑 JSON 时才可例外，并在需求或设计文档中记录适用页面、用途和确认依据；开发便利、管理员身份或配置复杂度均不能自行构成例外。

## 示例：初始化向导的员工类型选项

“员工类型选项”应使用以下行式表单：

| 选项 ID | 选项名称 | 操作 |
| --- | --- | --- |
| 1 | 正式员工 | 删除 |

表格下方提供“新增一行”按钮，用户分别填写“选项 ID”和“选项名称”，保存时由系统生成接口所需的数据结构。上述内容仅为交互示例，不代表默认业务数据。

截图中的 JSON 文本框及“填写选项 ID 与名称，例如……”的 JSON 示例输入方式不符合本规范，应按此行式表单整改。本规范的建立不代表该页面已完成整改或上线。

## 设计与验收检查

- 用户能否不编写 JSON 就完成配置，包括读取已有配置、增加条目、修改条目、删除条目和保存？
- 每一行的字段含义是否清晰，校验提示是否能定位到具体行和字段，失败后是否保留输入？
- 如存在 JSON 编辑入口，是否有明确需求及确认依据，而非开发人员自行决定？

本规范约束用户交互方式，不改变接口的数据格式、存储结构或已确认的业务规则。
